# Prompt pour l'agent Replit — POC eTeamsys v4 (nav façon HubSpot, IA à crédits, gabarits sectoriels)

Colle ce prompt tel quel dans l'agent Replit du projet `eteamsys-copilote-poc`. Il part du principe que l'agent a accès à tout le dépôt existant (`server.js`, `public/index.html`, `README.md`, `data/`).

---

## Contexte à respecter absolument avant de commencer

Ce POC existe déjà et fonctionne selon une architecture précise : **un socle de données commun, alimenté par trois adaptateurs interchangeables** (HubSpot réel en lecture seule, Odoo non testé, CRM basique propriétaire eTeamsys). Ne recommence rien de zéro — étends l'existant.

Fichiers et éléments déjà en place, à réutiliser :
- `server.js` : fonctions `getHubspotOverview()`, `getHubspotContacts()`, `getOdooOverview()`, `getOdooContacts()`, `getCrmBasiqueOverview()`, `getCrmBasiqueContacts()`, `buildBriefing()`, `askCopilot()`, `buildCopilotContext()`. Routes existantes : `GET /api/overview`, `GET /api/contacts`, `POST /api/copilot/ask`, `GET/POST /api/crm-basique/contacts`, `POST /api/leads/capture`, `GET /api/lp-stats`, `POST /api/crm-basique/import`.
- `public/index.html` : variable `currentSource` (hubspot/odoo/crm-basique), fonctions `render()`, `wireSegmentClicks()`, `openContactsModal()`, `renderCrmBasiqueAdmin()`, `askCopilotUI()`.
- Un **pattern "mode démo" déjà validé** : quand une source n'est pas configurée (pas de token), l'app affiche un badge DÉMO + des données d'exemple clairement fictives (noms suffixés "(exemple)") plutôt qu'un champ désactivé. **Réutilise ce pattern pour tout nouveau module ci-dessous — ne réinvente rien.**

Règles non négociables, quel que soit le module construit :

1. **Honnêteté de scope obligatoire.** Toute donnée simulée doit être visuellement marquée (badge DÉMO) et expliquée en une phrase. Ne jamais faire passer une simulation pour une intégration réelle.
2. **Le copilote IA reste strictement en lecture seule.** Aucune action irréversible (créer, modifier, envoyer) ne doit être exécutée sans une confirmation humaine explicite — et pour cette version, ne construis aucune action d'écriture réelle du tout, seulement des suggestions/réponses.
3. **Ne construis aucune vraie passerelle de paiement.** Le système de crédits (point 4) est une simulation interne (compteur en base JSON), pas une intégration Stripe/PayPal.
4. **Ne construis aucun vrai flux OAuth Google, ni aucun vrai appel aux API SEOCruz / SEA Copilot tant que les identifiants ne sont pas fournis dans les Secrets Replit.** Prépare l'adaptateur (même structure que `odooCall`), documente la variable d'environnement attendue, et fais tourner ces modules en mode démo par défaut — exactement comme Odoo aujourd'hui.
5. **Garde le sélecteur de source (HubSpot / Odoo / CRM basique) accessible** — c'est l'outil de test interne qui permet de valider les 3 backends sur la même interface. Ne le supprime pas, déplace-le simplement dans un espace clairement identifié comme outil de test (ex. un panneau "Compte de démonstration" séparé de la navigation principale), pour ne pas le confondre avec un réglage qu'un vrai client verrait.

## 1. Nouvelle navigation façon HubSpot

Remplace le tableau de bord actuel (page unique) par une structure à sidebar gauche, inspirée du menu HubSpot (capture fournie), avec ces entrées dans cet ordre : **Contacts, Entreprises, Transactions, E-mails marketing, SEO, Réseaux sociaux, Publicités, Formulaires, Pages de destination, Pages de site web, Tableaux de bord.**

- Chaque entrée devient une vue/page distincte (routing côté client simple, pas besoin d'un framework SPA — un `<div>` par section suffit, affiché/masqué en JS, comme le fait déjà `render()` aujourd'hui).
- Contacts et Entreprises sont **débloqués par défaut**. Tous les autres modules sont visibles dans la nav mais **verrouillés** tant qu'ils ne sont pas "souscrits" pour le compte de démonstration (utilise le pattern badge DÉMO généralisé : contenu visible avec données d'exemple, mention claire "module non activé — aperçu").
- Garde l'identité visuelle déjà posée dans le POC (cartes sombres, badges, typographie) plutôt que de copier HubSpot au pixel près — c'est le *principe* de navigation qui s'inspire de HubSpot, pas la charte graphique.
- Le module **Entreprises** n'existe pas encore comme entité à part dans le POC : pour HubSpot, utilise l'objet `companies` (déjà dans le scope `crm.objects.companies.read`, déjà lu partiellement dans `getHubspotOverview`) ; pour Odoo, `res.partner` avec `is_company: true` ; pour le CRM basique, regroupe les contacts par leur champ `société` en "entreprises virtuelles" — indique clairement dans l'UI que c'est une vue dérivée, pas une vraie table d'entreprises, pour cette dernière source.

## 2. Assistant IA façon "Breeze" (panneau latéral + suggestions)

Remplace la barre "Demandez au copilote…" actuelle par un panneau latéral (docké à droite, comme la capture Breeze Assistant), avec :

- Un message d'accueil personnalisé : "Posez-moi toutes vos questions, {prénom de l'utilisateur}" (le prénom peut être une valeur de config simple pour l'instant, pas un vrai compte utilisateur).
- Une section **"Suggéré"** listant 2 à 4 suggestions proactives, calculées à partir des vraies données de `getXOverview()` — pas inventées. Exemples à calculer réellement : nombre de contacts sans propriétaire/non assignés, nombre de nouveaux leads à relancer (déjà dispo via `relanceItems`), campagnes ou pages nécessitant une action. Si une source n'a pas l'équivalent (ex. CRM basique n'a pas de notion de "propriétaire"), n'affiche pas de suggestion inventée pour ce cas — affiche seulement celles qui ont un vrai sens pour la source active.
- Une rangée de boutons rapides façon Breeze : **Résumé** (appelle le copilote avec une question pré-remplie type "fais-moi un résumé de mon activité"), **Comment faire** (Q&A libre, réutilise `askCopilot`). **Créer** et **Réunions** : ne construis PAS de vraie action derrière ces deux boutons (ça impliquerait de l'écriture) — affiche-les désactivés avec une info-bulle "Bientôt disponible" pour respecter la règle n°2 ci-dessus.
- Le champ de saisie libre existant (`askCopilotUI`) est conservé tel quel dans ce panneau.

## 3 et 14. Tableau de bord adapté au secteur d'activité du client

Le compte de démonstration doit pouvoir être associé à l'un des 7 secteurs déjà définis dans notre cadrage produit. Ajoute un réglage simple (dans le panneau "Compte de démonstration" mentionné plus haut) : une liste déroulante "Secteur d'activité", avec ces 7 valeurs et leurs métadonnées associées (à coder en dur dans un objet JS/JSON, pas besoin de base de données) :

1. **E-commerce** — Objectif : croissance des ventes en ligne. Besoin : définir l'audience cible, identifier des niches produit, réduire le coût d'acquisition. Modules clés : Acquisition + Copilote (attribution par campagne/produit).
2. **Promoteur immobilier / constructeur de maisons** — Objectif : remplir le showroom / la maison témoin. Besoin : visites qualifiées, leads triés par budget et échéance d'achat, suivi sur cycle long. Modules clés : Acquisition (SEA local) + CRM + Copilote (scoring, MQL/SQL, relance).
3. **Fabricant/installateur (vérandas, fenêtres, aménagement extérieur)** — Objectif : volume de devis. Besoin : qualification rapide (zone, budget, urgence), relance quasi immédiate. Modules clés : Acquisition + SEO local + Copilote (score temps réel + brouillon de relance).
4. **Services B2B (agences, cabinets, consultants)** — Objectif : pipeline commercial qualifié. Besoin : qualification des demandes entrantes, nurturing long, priorisation commerciale. Modules clés : CRM + Copilote (MQL/SQL + séquences de nurturing).
5. **Retail multi-points de vente / franchise** — Objectif : trafic en magasin. Besoin : trafic localisé, attribution online-to-offline. Modules clés : Acquisition (SEA/SEO local) + Copilote (attribution).
6. **Pharma / santé** — Objectif : génération de leads conformes. Besoin : ciblage fin pro santé vs grand public, contraintes réglementaires. Modules clés : Acquisition (ciblage fin) + CRM + Copilote (contenu contrôlé).
7. **Artisans / TPE locales** — Objectif : simplicité, gain de temps. Besoin : CRM basique, relance automatique, peu de temps disponible. Modules clés : CRM basique + Copilote (score simple).

Le module **Tableaux de bord** (dernière entrée de la nav) devient la vue de synthèse : elle affiche le secteur sélectionné, son objectif principal, son besoin spécifique, et met en avant les KPI/modules listés comme "clés" pour ce secteur (ceux-ci apparaissent en premier / mis en évidence, les autres modules restent visibles mais en second plan). Reste sur le principe déjà validé du **briefing narratif en langage naturel** plutôt qu'une simple grille de KPI bruts.

## 4. Facturation de l'IA par crédits (simulation)

Ajoute un compteur de crédits par compte de démonstration (champ dans `data/crm-basique.json` ou un fichier de config séparé, ex. `data/credits.json` : `{ solde: number, historique: [...] }`).

- Chaque appel à `askCopilot` (question libre, "Résumé", suggestion cliquée) décrémente le solde d'un montant fixe (ex. 1 crédit par question — mets une constante facilement modifiable en tête de fichier).
- Si le solde atteint 0, l'assistant répond clairement "Crédits épuisés" plutôt que d'échouer silencieusement, avec un bouton "Recharger (simulation)" qui ajoute des crédits fictifs sans aucun vrai paiement — étiqueté explicitement comme simulation dans l'UI et le README.
- Affiche le solde courant quelque part dans le panneau assistant (ex. "12 crédits restants").

## 5. Positionnement : IA eTeamsys plutôt que Breeze pour les comptes avec CRM existant

Quand la source active est HubSpot ou Odoo (un CRM existant), l'assistant reste le nôtre (pas d'appel à l'IA native de HubSpot) — c'est déjà le cas techniquement (`askCopilot` ne dépend pas de la source). Ajoute simplement une ligne de contexte visible dans le panneau assistant pour ces deux sources, du type : *"Cet assistant tourne sur la plateforme eTeamsys — une alternative à l'IA native de votre CRM, à moindre coût."* Ne mets pas de chiffre de prix en dur (pas encore décidé) — laisse un espace réservé clairement signalé comme tel dans le code (`{/* TODO: tarif à confirmer */}` ou équivalent).

## 6. Module Transactions — funnel simplifié pour les comptes sans CRM existant

Pour la source **CRM basique uniquement**, remplace/complète le statut actuel du contact (lead/qualifié/client) par une vraie petite entité "transaction" : chaque contact peut avoir zéro ou plusieurs transactions, chacune avec un stade parmi exactement ces 5 valeurs : **Initiation → Offre envoyée → Négociation → Won → Lost**. Stocke ça dans `data/crm-basique.json` (un tableau `transactions` avec `contactId`, `stade`, `montant` optionnel, `creeLe`). Ajoute les routes minimales : lister les transactions, en créer une, changer son stade. Le module **Transactions** de la nav affiche, pour cette source, un funnel visuel des 5 stades (réutilise le principe du funnel déjà existant dans `getCrmBasiqueOverview`/le rendu actuel — ne construis pas un second système de funnel en parallèle).

Pour HubSpot et Odoo, le module Transactions affiche simplement les données de pipeline déjà lues (`getHubspotOverview`/`getOdooOverview`) — aucun changement de logique, juste un nouvel emplacement dans la nav plutôt que noyé dans l'ancien tableau de bord unique.

## 7. Module E-mails marketing — décision à prendre avant de coder

Le choix n'est pas tranché entre deux options pour les comptes sans CRM existant :
- **Option 1** : un vrai outil de suivi d'envoi d'e-mails simplifié (composer/envoyer depuis la plateforme, avec suivi d'ouverture).
- **Option 2** : une simple liste de contacts à relancer par e-mail, l'utilisateur envoyant depuis sa propre messagerie.

**Recommandation : implémente l'Option 2 pour cette version.** Construire un vrai outil d'envoi (Option 1) veut dire gérer la délivrabilité, l'authentification SMTP/API d'un fournisseur d'e-mail, le tracking d'ouverture — un chantier à part entière, pas une case à cocher, et hors du principe déjà posé d'éviter de reconstruire une "usine à gaz" pour des besoins qui ne sont pas encore confirmés commercialement. L'Option 2 est un simple export/liste (nom, e-mail, dernier contact, raison de relance) déjà quasiment couvert par les données existantes (`relanceItems`). Si ce choix ne convient pas, il suffit de remplacer cette section par l'Option 1 dans une itération suivante — ne code pas les deux en parallèle.

## 8. Module SEO — connecter l'app SEOCruz (Replit)

Crée un adaptateur `seocruzCall()` sur le même modèle que `odooCall()` : variables d'environnement `SEOCRUZ_API_URL` et `SEOCRUZ_API_KEY` (à ajouter dans `.env.example`, vides par défaut). Sans ces variables configurées, le module SEO reste en mode démo (ce qu'il est déjà aujourd'hui, étiqueté "Aperçu — simulé") — ne change que l'étiquette pour dire clairement "connecteur prêt, en attente des identifiants de l'app SEOCruz" plutôt que "non fonctionnel". N'invente pas le format de réponse de l'API SEOCruz — laisse une fonction avec un TODO explicite tant que la vraie documentation de cette API n'est pas fournie par Mike.

## 9. Module Réseaux sociaux — non construit dans cette version

N'implémente pas de logique pour ce module maintenant. Affiche-le simplement verrouillé dans la nav avec un texte descriptif des deux capacités prévues plus tard : (1) bots d'automatisation (projet déjà réalisé ailleurs chez eTeamsys, à connecter plus tard), (2) campagnes gérées par l'équipe eTeamsys. Aucune donnée, même simulée, n'est nécessaire ici — un simple état "à venir".

## 10. Module Publicités — connecter l'app SEA Copilot (Replit)

Même traitement que le point 8 : adaptateur `seaCopilotCall()`, variables d'environnement `SEA_COPILOT_API_URL` / `SEA_COPILOT_API_KEY`, mode démo par défaut, TODO explicite sur le format réel de l'API en attendant la documentation.

## 11. Module Pages de destination — pas de constructeur pour le client

Le client ne crée jamais de page lui-même. Ce module affiche uniquement une liste en lecture seule des landing pages qu'eTeamsys a produites pour ce compte (réutilise/étend `data/crm-basique.json` avec un tableau `landingPages` : titre, url, statut publié/brouillon, date de création). Pas de formulaire de création de page dans l'UI cliente — juste une liste, cohérent avec le principe déjà acté que ces pages sont produites par dialogue entre l'équipe eTeamsys et l'IA, en dehors de la plateforme cliente. Peut réutiliser des données d'exemple déjà présentes via `/api/lp-stats` pour peupler la liste.

## 12. Module Formulaires — listing + analyse, avec ou sans CRM

Réutilise l'esprit de la capture d'écran fournie (colonnes : nom, vues de page, soumissions, taux, dernière mise à jour). Pour HubSpot : ajoute un appel réel à l'API Forms de HubSpot (`GET /marketing/v3/forms` ou `/form-integrations/v1/forms` selon ce qui est accessible avec le token) — **attention : ceci nécessite probablement un scope supplémentaire sur le token HubSpot actuel** (le token du POC n'a aujourd'hui que `crm.objects.contacts.read`, `crm.objects.deals.read`, `crm.objects.companies.read` — il faudra que Mike ajoute un scope formulaires, ex. `forms` ou `content`, dans les paramètres de l'app privée HubSpot avant que ce module puisse lire de vraies données). Sans ce scope, retombe en mode démo avec des données d'exemple façon capture d'écran. Pour Odoo et CRM basique : il n'existe pas de notion de formulaire — affiche un état "Pas de formulaires suivis pour cette source" plutôt que d'inventer des données.

## 13. Module Pages de site web — connecter Google Search Console

Adaptateur `googleSearchConsoleCall()` sur le même modèle, variables d'environnement `GOOGLE_SEARCH_CONSOLE_CLIENT_ID` / `GOOGLE_SEARCH_CONSOLE_CLIENT_SECRET` / `GOOGLE_SEARCH_CONSOLE_REFRESH_TOKEN` (l'authentification OAuth réelle est hors scope de cette itération — ne construis pas le flux OAuth complet maintenant, seulement l'appel API en supposant qu'un refresh token est fourni manuellement dans les Secrets). Sans ces variables, mode démo avec des données d'exemple (pages, impressions, clics, position moyenne). Comme pour les Pages de destination, aucune capacité de construction de page côté client — uniquement de la donnée en lecture.

## Phasage suggéré (le tout en une fois est trop gros pour une seule passe)

1. **Phase 1 — structure** : nouvelle nav sidebar (point 1), déplacement du sélecteur de source, panneau assistant façon Breeze avec suggestions réelles (point 2), système de crédits en simulation (point 4) + mention positionnement (point 5).
2. **Phase 2 — modules à données réelles/dérivées** : Entreprises, Transactions avec le nouveau funnel CRM basique (point 6), E-mails marketing en Option 2 (point 7), Pages de destination en lecture seule (point 11).
3. **Phase 3 — connecteurs externes en mode démo** : SEO/SEOCruz (point 8), Publicités/SEA Copilot (point 10), Formulaires (point 12), Pages de site web/GSC (point 13) — tous en mode démo tant que les identifiants réels ne sont pas fournis.
4. **Phase 4 — sectorisation** : gabarits des 7 secteurs et Tableau de bord de synthèse (points 3 et 14).
5. **Non fait dans cette itération** : Réseaux sociaux (point 9, juste un état "à venir").

## Definition of done

- Chaque nouveau module s'affiche sans erreur pour les 3 sources existantes (HubSpot, Odoo, CRM basique), avec un état honnête (réel / démo / non applicable) visible à l'écran.
- Le README est mis à jour avec la même rigueur que l'existant : pour chaque nouveau module, préciser explicitement ce qui est réel, testé, simulé, ou non applicable, et quelles variables d'environnement restent à configurer par Mike.
- Aucune régression sur les fonctionnalités déjà démontrées (drill-down contacts, copilote conversationnel de base, capture de leads, stats LP, import Excel du CRM basique).
